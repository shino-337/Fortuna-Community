# Security

This guide covers security-relevant configuration for running Fortuna. It is not an internal secure-coding standard.

## Authentication

Core uses JWT authentication for dashboard/API users.

- Configure `FORTUNA_JWT_SECRET` before creating `fortuna-secrets`.
- Use a long random value, for example `openssl rand -base64 32`.
- Rotate the secret intentionally because existing sessions become invalid.

## Default Admin

Fresh deployments create an `admin` user.

- Preferred: set `FORTUNA_ADMIN_PASSWORD` before running `./scripts/utils/ensure-fortuna-secrets.sh`.
- Local bootstrap fallback: if no admin password is provided, the default is `Fortuna_ChangeMe_123!`.
- When the bootstrap default is active, Fortuna requires an immediate password change before normal API/UI use.
- Existing databases keep the current admin password. Core does not reset an existing admin back to the bootstrap default.

## Kubernetes Secrets

Create application secrets with:

```bash
./scripts/utils/ensure-fortuna-secrets.sh fortuna
```

Expected inputs for production:

| Variable | Purpose |
|----------|---------|
| `FORTUNA_DATABASE_URL` | Core PostgreSQL connection string |
| `FORTUNA_POSTGRES_PASSWORD` | Bundled PostgreSQL password, when using bundled PostgreSQL |
| `FORTUNA_JWT_SECRET` | JWT signing secret |
| `FORTUNA_ADMIN_PASSWORD` | Initial admin password |
| `FORTUNA_INGEST_TOKEN` | Core/Agent ingest token; generated by `ensure-fortuna-secrets.sh` when omitted |
| `POD_DETAIL_ENCRYPTION_KEY` | Optional pod detail encryption key |

Do not commit real secret values. Use environment variables, Kubernetes secrets, or your external secret manager.

## mTLS

Core and Agent communicate with mTLS by default.

```bash
NAMESPACE=fortuna ./scripts/utils/create_mtls_secret.sh
```

The script creates or preserves:

- `fortuna-core-tls`
- `fortuna-agent-tls`
- `fortuna-ca-cert`
- `fortuna-webhook-tls`

Use `MTLS_REGEN=1` only when intentionally rotating certificates.

## Image Pull Credentials

Published images are hosted under:

```text
ghcr.io/shino-337/fortuna-community
```

If packages are private, create `ghcr-pull` with a token that has `read:packages`, then patch the Fortuna service accounts. See [Quickstart](../01-getting-started/QUICKSTART.md).

## Runtime Sensors

Falco and eBPF integrations can expose sensitive runtime information such as process names, command lines, and network destinations. Restrict access to runtime pages and API routes to users who need operational security visibility.

## Database Handling

- Back up PostgreSQL before production upgrades or destructive resets.
- Use `--db-reset` only for local/dev rebuilds unless you have a recovery plan.
- After a DB reset, reload CVE data before using CVE or supply-chain views for decisions.

## Public Repository Hygiene

Before pushing:

- Check that no credentials, kubeconfigs, tokens, private screenshots, generated reports, or local test artifacts are staged.
- Keep generated E2E output local unless it has been reviewed and redacted.
- Prefer published image tags (`latest`, `sha-<commit>`, or `v*` release tags) in user-facing docs.
